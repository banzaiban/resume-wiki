# Agent 状态持久化与话题切换

> tags: llm-agent, 状态持久化, checkpoint, 会话恢复, 话题切换
> weight: 1
> updated: 2026-08-04

## 核心结论
高并发下不丢会话：Agent 循环每步把状态 checkpoint 落库（Redis 热数据 + MySQL/MongoDB 冷数据），请求按 session_id 路由，任何一步崩溃都从最近快照恢复。用户突然切话题：意图检测识别切换 → 当前话题状态压栈/快照保存 → 新话题开新分支，切回时可恢复现场。

## 展开
- **状态内容**：对话历史、当前计划/步骤进度、工具中间结果、待办事项——即恢复执行所需的最小完整快照（LangGraph 的 State checkpoint 即此思路）。
- **持久化策略**：
  - 每步写 Redis（低延迟，会话级 TTL），异步刷冷库；
  - 崩溃恢复：读取最近 checkpoint 续跑，未完成的工具调用按幂等键去重；
  - 多实例部署：状态外置（不进进程内存），任意实例都能接棒 → 水平扩展无碍。
- **话题切换**（状态机上下文切换）：
  1. 意图分类/状态机检测到话题跳变（与当前任务无关的新意图）；
  2. 当前话题的状态栈快照保存（含进度），新开话题上下文；
  3. 用户回到原话题时弹出栈顶恢复（"我们刚才说到…"）；
  4. 多话题并存时注意上下文污染——新话题不应带上无关旧上下文。
- 高并发关注点：写放大（每步写库）→ 批量/异步落盘；热点 session 用本地缓存 + 最终一致。

## 关键细节 / 易错点
- 追问"为什么状态不能放进程内存"：实例重启/扩容/负载均衡换机就丢会话——状态外置是会话服务可伸缩的前提。
- 追问"checkpoint 粒度"：每步一快照恢复最精细但写多；可关键节点（计划完成、工具成功）才快照，权衡写开销与丢失窗口。

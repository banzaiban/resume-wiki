# 评测数据集构建

> tags: llm-agent, evaluation, 评测集, 数据标注, benchmark
> weight: 1
> updated: 2026-07-30

## 核心结论
从线上日志**分层抽样**真实 query（按意图/频段/时间分层），人工标注意图和关键信息作为 golden label，再混入历史请求做增强，确保短头和长尾都有覆盖。评测集要定期更新防止过拟合和分布漂移。

## 展开
- **来源**：优先线上真实流量（分布真实），而非人工造题。分层维度：意图类别、query 频率（高频短头 vs 长尾）、难度、时间段。
- **标注**：意图标签 + 关键槽位/期望答案要点。多人标注 + 交叉校验（标注一致性 kappa），有争议的 case 升级仲裁。
- **增强**：历史请求改写（同义改写、错别字注入、口语化）扩充覆盖；对抗样本（边界 case、易混意图对）专门加密度。
- **指标设计**：分类任务用准确率/F1（分类别看，不只看整体）；生成任务用要点命中率、LLM-as-judge 打分 + 人工抽检对齐；端到端 Agent 用任务完成率、工具调用正确率。
- **防泄漏与防过拟合**：评测集不进训练数据；定期（如每季度）换血一部分；线上新 bad case 持续补充进来。

## 关键细节 / 易错点
- 只用高频 query 会高估效果，长尾才是真实水位——所以要**分层**而不是随机抽。
- LLM-as-judge 要校准：抽样与人工评分对齐，给 judge 明确 rubric，防止位置偏差/长度偏差。
- 追问"评测集多大够用"：分类每类至少几十上百条；关键是覆盖度而非绝对数量。
- 追问"线上线下指标不一致"：检查评测集分布是否漂移、是否泄漏进训练集。

# Bad Case 分析方法论

> tags: llm-agent, bad-case, 复盘, 迭代闭环, 数据飞轮
> updated: 2026-07-30

## 核心结论
建坏例库并打分类标签（意图错、工具挂、检索差、生成差等）→ 定期复盘看分布 → 按归因分派修复手段：规则能兜的改规则、prompt 能修的改 prompt、系统性问题反哺训练数据/微调 → 修复后回归验证，形成数据飞轮。

## 展开
- **收集渠道**：用户负反馈（点踩/投诉）、人工抽检、自动检测（低置信度、异常步数、工具连续失败）、客服升级 case。
- **标签体系**：按故障环节分——意图识别错、检索召回差、工具调用挂（选错/参数错/下游故障）、生成质量差（幻觉/格式错/答非所问）、上下文丢失。一个 case 可多标签。
- **复盘节奏**：定期（如每月）看标签分布和趋势，抓 top 问题集中修，而不是逐个 case 零敲碎打。
- **修复手段分层**（成本从低到高）：
  1. 规则/黑白名单：见效最快，适合明确的硬 case；
  2. 改 prompt / few-shot 例子：覆盖一类表达问题；
  3. 检索/工具层修复：补文档、修工具 schema；
  4. 反哺训练数据重训/微调：系统性能力问题才动模型。
- **闭环验证**：修复的 case 进回归评测集，防止改 A 坏 B；观察线上同类 case 是否下降。

## 关键细节 / 易错点
- 先归因再修：同一个"答错了"表象可能是检索没召回（补数据）也可能是生成忽略了上下文（改 prompt），修错层白费功夫。
- 坏例库本身要去重和聚类（embedding 聚类），否则高频问题会被重复统计淹没长尾。
- 追问"怎么自动发现 bad case"：低置信度采样、用户行为信号（重复提问、立刻转人工）、LLM-as-judge 抽检。
- 追问"改 prompt 会不会按下葫芦浮起瓢"：会，所以必须有回归评测集把关。

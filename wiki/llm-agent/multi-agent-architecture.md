# Multi-Agent 架构：中心化编排 vs P2P、拆分边界、通信优化

> tags: llm-agent, multi-agent, supervisor, p2p, a2a, 拆分, 通信
> weight: 4
> updated: 2026-08-04

## 核心结论
两类拓扑：中心化编排（supervisor/orchestrator 统一分派，分层架构）vs P2P（agent 点对点直连协作，A2A 协议）。中心化可控、可观测、易调试，但有单点瓶颈；P2P 灵活、无单点，但链路不可预测。单体拆多体的边界：职责/工具集正交、上下文可隔离、有并行或独立伸缩收益时才拆；步骤强耦合共享上下文的不该拆。通信损耗靠结构化状态传递、共享黑板记忆、摘要压缩来控制。

## 展开
- **中心化编排（分层）**：supervisor 理解任务 → 分派给专家 agent → 汇总结果。优势：全局状态集中、决策路径可观测、易加审批/降级；劣势：supervisor 是能力与吞吐瓶颈、每层转发都有信息损耗。
- **P2P 架构**：agent 间直接发消息（A2A 协议：任务委派、状态同步、产物传递）。优势：拓扑灵活、可动态组队、无单点；劣势：全局一致性与调试难、消息风暴风险。
- **单体拆多体的判断**：
  - 该拆：① 单 agent 上下文超限（工具+领域知识塞不下）；② 职责边界清晰且工具集正交（检索 agent / 执行 agent / 审核 agent）；③ 子任务可并行，拆分有延迟收益；④ 某环节需独立扩容或独立模型（贵模型只做规划）。
  - 不该拆：步骤间强耦合、需要共享大量中间上下文（拆后通信成本 > 收益）；链路短、单 agent 没到上限——先把单体调到上限。
- **通信损耗优化**（防冗余信息导致决策效率下降）：
  1. 传结构化状态（schema 化的任务卡/结果对象）而非整段对话原文；
  2. 交接时传摘要 + 指针（需要细节再回查），不复制全量上下文；
  3. supervisor 只做路由不转述内容，减少层层复述的信息失真。
- **共享全局空间记忆**（解决各 agent 上下文理解不一致）：黑板模式/共享 state store——所有 agent 读写同一份结构化世界状态（统一 schema、术语表、版本号），局部上下文各自维护、全局事实以黑板为准；写冲突用版本/锁消解。

## 关键细节 / 易错点
- 追问"多 Agent 一定更好吗"：不——token 成本倍增、错误级联（上游错下游放大）、调试难；有明确收益才拆。
- 追问"中心化 vs 点对点怎么选"：强管控/强审计场景中心化；开放协作、agent 数量动态变化场景 P2P；实践常混合（组内中心化、组间 P2P）。

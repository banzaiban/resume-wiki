# 大模型 API 工程：限流应对、API vs 本地部署、上下文缓存

> tags: llm-agent, 限流, rate-limit, 部署选型, prompt-caching, 上下文缓存
> weight: 3
> updated: 2026-08-04

## 核心结论
API 限流的工程手段：客户端匀速排队（令牌桶）+ 指数退避重试 + 多 key/多 provider 轮询 + 非关键路径降级小模型。API vs 本地部署选型看：数据合规、成本曲线、延迟、模型能力需求、运维能力。上下文缓存（prompt caching）让重复前缀（系统指令/工具 schema）只算一次钱一次算力，是 Agent 高频调用的降本关键。

## 展开
- **限流应对**（大模型 API 常见 RPM/TPM 限制）：
  1. 请求队列 + 令牌桶匀速发送，把突发削平到限额内；
  2. 429/5xx 指数退避 + jitter 重试，尊重 Retry-After；
  3. 多 API key / 多 provider 池化轮询，单点限流自动切换；
  4. 降级链：主模型限流 → 备用模型/小模型 → 缓存答案；
  5. 源头减量：prompt 瘦身、合并调用、结果缓存（相同 query 直接命中）。
- **API 调用 vs 本地部署选型因素**：
  - 选 API：模型能力要求高（旗舰闭源）、业务量小或波动大、无运维团队、快速验证期；
  - 选本地部署：数据敏感/合规要求不出内网、调用量大到 API 成本超过自建 GPU、需要微调/私有定制、延迟要求极致（内网）；
  - 中间态：小模型本地（分类/embedding）+ 大模型 API 的混合架构最常见。
- **上下文缓存（prompt caching）**：Agent 每轮请求都带相同的系统指令 + 工具 schema + 历史，前缀 KV 可复用——缓存命中部分只收低价/零价且首 token 更快。优势：降成本（冗余系统指令不重复计费）、降延迟。用法：把稳定内容放 prompt 前缀（缓存按前缀匹配），变化内容放后面；注意缓存 TTL 与最小长度门槛。

## 关键细节 / 易错点
- 追问"限流时直接重试有什么问题"：无退避重试加剧拥塞（惊群）；且非幂等写操作重试有重复风险。
- 追问"本地部署隐形成本"：GPU 采购/闲置、推理框架调优（vLLM）、模型升级维护——小团队算账常漏运维人力。
- 上下文缓存按**前缀**匹配：指令里插入每轮变化的内容（如时间戳）会击穿缓存。

# HashMap 底层原理

> tags: java, hashmap, 红黑树, 扩容, 并发
> weight: 1
> updated: 2026-07-30

## 核心结论
JDK 8 的 HashMap = 数组 + 链表 / 红黑树。put 时对 key 的 hashCode 做扰动（高 16 位异或低 16 位）再 `& (n-1)` 定位桶；冲突先挂链表，链表长度 ≥ 8 **且数组长度 ≥ 64** 时转红黑树（查询从 O(n) 降到 O(log n)），元素减到 ≤ 6 退化回链表。负载因子 0.75，size 超过阈值扩容为 2 倍。

## 展开
- **为什么容量是 2 的幂**：`hash & (n-1)` 等价于取模但快得多；且扩容时元素要么留原位、要么移动到 `原索引 + 旧容量`，判断只需看 hash 新增的那一位是 0 还是 1，无需重新计算 hash。
- **扰动函数**：`h ^ (h >>> 16)`，让高位也参与索引计算，减少低位相同导致的碰撞。
- **为什么阈值是 8**：泊松分布下理想哈希时链表长度到 8 的概率约千万分之一，出现说明 hash 分布异常，才值得付出树化成本。数组长度 < 64 时优先扩容而非树化（小表冲突多半是容量不够）。
- **负载因子 0.75**：空间与冲突概率的折中，太大冲突多、太小浪费内存。
- **JDK 7 → 8 的变化**：头插法改尾插法（7 的头插在并发扩容时可能形成环形链表导致 CPU 100%）；引入红黑树。
- **线程不安全**：并发 put 可能丢数据、size 不准；并发场景用 ConcurrentHashMap（JDK 8 用 CAS + synchronized 锁单个桶，锁粒度比 7 的分段锁更细）。

## 关键细节 / 易错点
- 树化的**两个**条件都要说（链表≥8 且表长≥64），只说一个是常见扣分点。
- 追问"为什么用红黑树不用 AVL"：红黑树插入删除旋转次数少，综合读写性能更均衡。
- 追问"key 为什么建议不可变"：hashCode 变了就找不回原桶，如 String/Integer 天然适合。
- 追问"hashCode 和 equals 的契约"：equals 相等则 hashCode 必须相等，否则 map 行为错乱。
- 追问"ConcurrentHashMap 的 size 怎么算"：baseCount + CounterCell 数组，避免单点竞争。

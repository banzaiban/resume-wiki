# 业务数据的多数据库选型

> tags: database, mysql, redis, 向量库, elasticsearch, neo4j, 选型
> weight: 2
> wrong: 1
> updated: 2026-07-30

## 核心结论
按数据形态和访问模式分工：MySQL 存核心业务（强一致、事务）、Redis 做缓存/会话（低延迟 KV）、向量库存 embedding（相似度检索）、ES 做日志与全文搜索（倒排索引）、图数据库 Neo4j 放知识图谱（多跳关系查询）。

## 展开
| 存储 | 数据形态 | 核心能力 | 典型场景 |
|---|---|---|---|
| MySQL | 结构化、关系型 | ACID 事务、二级索引 | 订单、账户等核心业务 |
| Redis | KV/丰富数据结构 | 内存级延迟、TTL | 会话、缓存、限流、排行榜 |
| 向量库 (Milvus/pgvector) | 高维向量 | ANN 近似检索 (HNSW/IVF) | RAG 召回、语义搜索、推荐 |
| Elasticsearch | 半结构化文档 | 倒排索引、全文检索、聚合 | 日志检索、站内搜索 |
| Neo4j | 节点+边 | 多跳图遍历 (Cypher) | 知识图谱、关系链路（SQL 多跳 join 会爆炸） |

- 选型思路先问三件事：数据结构（关系/KV/文档/向量/图）、查询模式（点查/范围/全文/相似度/图遍历）、一致性与规模要求。
- 多存储并存的代价：数据同步（binlog → CDC 同步到 ES/缓存）、一致性（缓存与 DB 的双写问题）、运维成本。不要为了技术堆技术，够用优先。

## 关键细节 / 易错点
- 追问"缓存一致性"：Cache Aside（**先更 DB 再删缓存**，删而不是更，靠读时懒加载重建）+ 延迟双删 / binlog 订阅删缓存。
  - 脏数据时序（先删缓存再更 DB）：删完后读请求 miss → 读旧 DB 值 → 回填缓存 → DB 才更新完 → 缓存留旧值；延迟双删的第二次删就是清这个回填。
  - 脏数据时序（先更 DB 再删缓存）：读请求在缓存失效瞬间读了旧 DB 值，写请求更完 DB 删完缓存后，读请求才把旧值写回——要求"读比写慢"，概率低，所以 Cache Aside 被认为够用。
- 追问"为什么 ES 不能当主库"：主库=source of truth（业务权威存储）。① 近实时，写后要等 refresh（~1s）可见，读己之写都不保证；② 无跨文档事务；③ 深分页弱、mapping 变更要重建索引、历史有脑裂丢数据前科。定位是 MySQL 的检索副本（binlog/CDC 同步）。
- 追问"pgvector 和专用向量库怎么选"：数据量小（<百万级）用 pgvector 省运维；大规模、高 QPS 用 Milvus 等专用库。
- 追问"图数据库什么时候真的需要"：≥3 跳的关系查询、路径分析。两跳以内 MySQL join 就够，上 Neo4j 是没必要（多一套存储的运维+同步成本）而非不能。为什么深跳数图库快：SQL 多跳 join 中间结果组合爆炸，图库按邻接遍历、代价只和节点度数成正比。

# TCP 与 UDP 的区别及选型

> tags: network, tcp, udp, 丢包, 实时通信
> weight: 1
> updated: 2026-07-30

## 核心结论
TCP 面向连接、可靠、保证顺序、有流量控制和拥塞控制，适合文件传输、网页、API；UDP 无连接、不保证可靠和顺序，头部小、延迟低，适合实时音视频、在线游戏、DNS。实时游戏选 UDP——延迟比丢几个包更致命，丢包用冗余发送、前向纠错和客户端插值预测来弥补。

## 展开
**对比**
| 维度 | TCP | UDP |
|---|---|---|
| 连接 | 三次握手建连、四次挥手断开 | 无连接，直接发 |
| 可靠性 | 确认重传保证不丢不乱序 | 尽力而为，可能丢包/乱序/重复 |
| 头部 | 20 字节起 | 8 字节 |
| 拥塞控制 | 有（慢启动/拥塞避免/快重传快恢复） | 无（可能压垮网络，也意味着不会被拥塞窗口拖慢） |
| 传输方式 | 字节流（有粘包问题，需应用层定边界） | 数据报（保留消息边界） |
| 适用 | HTTP、文件、数据库 | 音视频、游戏、DNS、QUIC 底层 |

**为什么实时游戏用 UDP**：TCP 的队头阻塞——丢一个包，后面已到达的包也要等重传完才能交付，造成卡顿尖峰；游戏里旧的位置数据重传过来也没用了，不如直接用新数据。

**UDP 丢包导致动作不同步的排查与修复**（分层答）：
1. 定位：抓包（tcpdump/Wireshark）看丢包率和序列号断点，分清是网络丢、还是接收缓冲区溢出（`netstat -su` 看 UDP receive errors），排查 MTU 分片、限速、NAT 超时。
2. 应用层可靠性：自定义包序号 + ACK + 选择性重传（只对关键指令可靠传输，位置同步这类可丢）。
3. 抗丢包：冗余发送（每个包带上前 N 帧数据）、FEC 前向纠错。
4. 逻辑层：客户端预测 + 服务器权威校正 + 插值/回滚（rollback netcode），让画面平滑；定期全量状态同步纠偏。

## 关键细节 / 易错点
- "UDP 不可靠"不等于"不能可靠"——QUIC/KCP 就是在 UDP 上实现可靠传输，同时避免 TCP 的队头阻塞和内核栈僵化。
- 粘包只是 TCP 的问题（字节流），UDP 保留边界。
- 追问"三次握手为什么不是两次"：防止历史失效连接请求建立连接，且需双向确认初始序列号。
- 追问"QUIC 为什么基于 UDP"：在用户态实现可靠+多路复用，避免队头阻塞、0-RTT 建连、可快速迭代（不受内核升级限制）。
